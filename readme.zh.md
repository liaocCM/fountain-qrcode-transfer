# fqt

[English](readme.md)

用螢幕和鏡頭傳檔案 — 一邊播 QR 動畫,一邊用相機拍。不用網路、不用配對。

實測:Logitech C270(百元級定焦 webcam,1280×960 @ 30fps)**~42 KB/s**,
iPhone 當鏡頭 **~195 KB/s**([詳細數據](docs/results.md))。

iPhone 的數字還沒嚴格測完,理論上更快(當時相機只跑在 24–30fps,
若餵到 60fps 上限翻倍)。

## 安裝

```bash
python3 -m venv .venv
.venv/bin/pip install -e .
```

全部是預編譯 wheel,不用編譯器。macOS / Windows / Linux 都能跑。

## 使用

發送(範例用 40fps,搭配 30fps 的相機;fps 依你的相機自己調,原則見下面訣竅):

```bash
fqt send 檔案.pdf --fps 40
```

播放中可按:`[` `]` 調 fps · `g` 每幀幾顆碼 · `p` 單碼容量 · `q` 結束。

接收:

```bash
fqt recv --fps 30 --preview --out 收檔資料夾/
```

用預覽視窗對準,然後看狀態列:`sharp` 是對焦(100 能用、300 很清楚),
`yield` 是解碼率。存檔前會驗 SHA-256。

重要的訣竅就三個:

- 相機架穩,手持是吞吐量殺手
- 發送 fps 跟相機 fps **錯開**(相機 30 → 發送開 40)
- 光線越亮、曝光越短、廢片越少

自動找出你設備的最佳參數:

```bash
fqt sweep --camera 0 --kb 300 --configs "40:2x1:far,40:2x2:far,36:2x2:far"
```

## 各種相機的理論上限

上限 = 每幀容量 × 相機 fps。解析度決定塞得下多大的 QR 網格(每個模組至少要
~3 個相機像素),fps 決定每秒能收幾張:

| 相機 | 塞得下的網格 | 理論上限 | 傳 10 MB(理論) | 實測 |
|---|---|---|---|---|
| 480p @ 30fps | 1×1 far | ~42 KB/s | ~4 分鐘 | — |
| 720p @ 30fps | 2×1 far | ~84 KB/s | ~2 分鐘 | — |
| C270(1280×960 @ 30fps) | 2×2 far | ~169 KB/s | ~1 分鐘 | 42 KB/s |
| 1080p @ 30fps | 3×2 far | ~253 KB/s | ~40 秒 | — |
| iPhone(1920×1440 @ 30fps) | 3×2 close | ~515 KB/s | ~20 秒 | ~195 KB/s |
| 同上,若跑滿 60fps | 3×2 close | ~1 MB/s | ~10 秒 | 未測 |
| 4K @ 60fps | 4×3 close | ~2 MB/s | ~5 秒 | 未測 |

實測通常是理論值的 2~5 折,差距來自 yield(曝光跨幀的廢片)、光線、對焦。

## 限制

- 甜蜜點 ≤ 10 MB(幾秒到幾分鐘),50 MB 可用,**上限 190 MB**
  (表頭欄位:`k` 是 u16、`totalLen` 是 u32)。文字/JSON 會先壓縮,實際快好幾倍
- 整個檔案在接收端 RAM 裡拼裝
- 接收端中斷就要重來
- 沒有加密:誰的相機拍得到你的螢幕,誰就收得到

這些都有解法(v2 表頭加寬、分段傳輸、斷點續傳),擴充後大小就沒有實質上限
— 但速度還是 ~195 KB/s,時間才是真正的牆:

| 檔案 | 要等多久(iPhone 速度) |
|---|---|
| 500 MB | ~45 分鐘 |
| 4 GB | ~6 小時 |
| 10 GB | ~15 小時 |

## 原理

先講這個通道最麻煩的地方:它是單向的。相機漏拍了,沒辦法跟螢幕說「欸,
第 37 塊再播一次」。那最直覺的做法是什麼?把檔案切塊輪流播,漏了就等下一輪
轉回來。聽起來還行,但算一下就知道多慘:切成 1000 塊、只缺最後一塊的時候,
平均要再等 500 幀,越接近傳完越煎熬。

Fountain code 就是來解這個的。它的想法有點反直覺:與其播「某一塊」,不如
每一幀都播「隨機幾塊 XOR 起來的混合物」。要混哪幾塊,是用幀編號算出來的,
兩邊跑同一套算法,所以接收端看到編號就知道這幀混了什麼,完全不用溝通,
中途才開始看也行。

那混在一起要怎麼解開?其實就是解聯立方程式。運氣好收到只混一塊的幀,那塊
直接到手;已經解出來的塊,可以從其他幀裡 XOR 扣掉,扣著扣著某一幀只剩一個
未知數,又解出一塊新的,連鎖反應一路雪崩下去。數學上收到 k 幀再多一點點,
整個檔案就拼回來了。所以順序無所謂、漏拍也無所謂 — 手抖拍廢一張,代價是
半秒,資料永遠不會錯。

這個實作在上面又加了三件事讓它更快。第一,前 k 幀不混,直接把原始資料塊
照順序播一遍,收訊好的話一輪收完、零浪費,混合模式是之後拿來補洞的。
第二,一個畫面塞好幾顆 QR,每顆都是獨立的一幀,3×2 就是六倍。第三個比較
隱晦:相機是逐行曝光的(rolling shutter),很容易固定毀掉畫面同一區,
要是某塊每次都排在那區,它就永遠等不到,所以重播時會把塊的位置輪著換,
誰都不會一直卡在壞區。

你可能會問:QR 本身不是就有糾錯了嗎?有,但它管的是「一張碼髒了一角」,
我們遇到的是「整張拍糊了」。糊掉的整張丟掉就好,反正 fountain 會補,
所以碼內糾錯開最低檔(L),省下來的空間拿去裝資料。

最後,拼回來的檔案要先過 FNV-1a 再過 SHA-256,錯一個 bit 都存不下來;
傳之前會先 zstd 壓縮,文字類的東西實際快好幾倍。至於瓶頸,幾乎都在相機:
曝光跨到畫面切換的瞬間,拍出來就是兩幀疊影,整張報廢。這也是為什麼光線、
架穩、fps 錯開這三件事,比任何軟體優化都有用。

解碼是 zxing-cpp(C++),Python 只負責調度。wire format 細節在
[docs/design.md](docs/design.md)。
